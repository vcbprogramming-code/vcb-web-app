## Current state

- **Live deployed version:** @220 (deployment `…AKfycbxJN7ol…D19rUnr`)
- **Done:** App is live and stable. Deployment manifest is `ANYONE_ANONYMOUS` (no Google-account gate at the door). Reading a **🔓 Public** project requires no sign-in at all; a **🔒 Locked** project is readable only by admins, editors and the emails named on it. **Editing** always requires signing in. **Google Sign-In** is the primary route (the browser gets a signed ID token from Google; the server verifies it with Google before trusting it), with the email + password login kept as a fallback for anyone without a Google account or if the Google library cannot load. Set the `GOOGLE_CLIENT_ID` Script Property to enable it. Sessions are Script Property tokens remembered ~30 days. Access is three-tier: **admin** (`ADMIN_EMAILS` in `Config.js`, full control incl. access management), **editor** (self-service `EDITOR_EMAILS` list, managed from Settings → 🔐 Project access → Editors — can edit/create/delete meeting content, attachments, and file inbox recordings, but not hidden/pinned status, edit history, or access management). Each editor gets their **own account with a 4-digit PIN**, or an admin can enable one optional **shared team PIN** any listed editor may use (Settings → 🔐 Project access → Editors), with a Show/Hide toggle so the admin can look it up to tell someone, created by an admin in that same panel (**Set password**) and changed by the employee on first sign-in; passwords are stored salted and hashed in `EDITOR_CREDS`, never in plaintext. The ✎ Edit button is visible to everyone, and clicking it opens the login, because under `ANYONE_ANONYMOUS` Google never reveals a visitor's email to the script. Admin remains gated on the Google account or `ADMIN_PASSWORD`, never on an editor password, and **viewer** (per-project guest list, managed from Settings → 🔐 Project access, which is now a **full-page** workspace rather than a dialog). A project is either **🔓 Public** — readable by anyone who opens the app link, no sign-in, any domain — or **🔒 Locked**, readable only by admins, editors, and the specific emails named on it. A locked project is **not** open to the whole `@vcb-con.com` domain; a locked project with nobody named is admin/editor-only, and the panel warns while any project is in that state. Addresses can be pasted several at a time, and one project’s list copied onto others. The Sheet database is the sole source of truth — Docs-as-source-of-truth sync (`autoSync`/`importAllDocs`) is retired/disabled. Every content-changing mutation is recorded to an append-only `AUDIT_LOG` sheet with full pre-edit snapshots in a `Versions` sheet, surfaced via an in-app "Edit history" panel (admin-only). Meetings can carry uploaded file attachments (`attachments` column) and staff comments (`comments` column — 💬 button on the meeting detail bar opens a slide-out panel to post/read/delete; author-or-admin can delete). New/Edit meeting date field has a calendar-icon picker alongside the free-text input. Header "VCB Group" wordmark links back to the VCB Connect portal (opens full tab, i18n tooltip). Mobile home pane's "Latest meetings" tiles reserve a skeleton placeholder before data loads (no layout shift under the thumb), and opening a meeting from those tiles mid-boot can no longer get silently reverted back to the home pane. Each project dashboard has a "🔗 Share latest-meeting link" button — a `?project=<id>` permalink that always opens whatever is currently the latest meeting in that project, so a link can be pasted once and reused forever instead of re-sharing after every new meeting. Share links (`getExecUrl_`) are always the portable `/macros/s/.../exec` form, never a Workspace domain-scoped `/a/<domain>/` link that only opens for signed-in org accounts. Exported PDFs are named `<title> <d.m.yy>` (e.g. `VCB Meeting Minutes 18.8.69`) — dot-separated, unpadded, 2-digit Buddhist year, matching the convention already in use in the export folder. Page geometry is pinned in `@page` (`size:A4; margin:2.7cm 17mm 2cm`), so the reading view, editor and PDF break pages identically regardless of the print dialog's paper destination. Layout is responsive across desktop, tablet and phone: the A4 sheet sits in a fixed 860px page box and is CSS-scaled down when the reading pane is narrower (never clipped), the fixed columns narrow at 1200/1040px, and in tablet portrait the meeting list becomes a ☰ overlay so the document has room. Tablets deliberately take the **paginated** (desktop) render path and are scaled afterwards, so their page breaks still match the PDF; only phones use the continuous-document path. Guarded by three dependency-free scripts in `tools/layout-checks/` (device widths, CSS scoping/cascade, scaler arithmetic) — run them from the project root after touching the `.body` grid, the pane elements, or the scalers. React mirror (`meeting-minutes-react/`) kept in sync, including a push to the `vcb-web-app` GitHub monorepo (`VCB-dev` branch, `meeting-minutes/` folder).

## History

- **2026-08-29** — **The app is usable on iPads.** Reported as "not working on the iPad Air screen, and also iPad Pro": the meeting document was clipped along its left edge, showing "ภัณฑ์ก่อสร้าง จำกัด" where the letterhead reads "บริษัท วิจิตรภัณฑ์ก่อสร้าง จำกัด". The layout is a three-column grid whose only breakpoint was 1100px, so an iPad Pro (1024px) and iPad Air (820px) both got the narrowest desktop columns — 258 + 320 = 578px of fixed chrome, leaving ~446px and ~242px for a sheet that needs ~900px. Nothing scrolled to the lost text either: `#detailContent` scrolls vertically and `.frame-wrap` hides overflow-x, so the clipped part was simply unreachable. Fixes: (1) new 1200/1040/900px bands that narrow the fixed columns as width runs out; (2) in tablet **portrait** the meeting list stops being a column at all and becomes an overlay opened by a ☰ pill and dismissed by tapping the document — three columns cannot fit 820px, and forcing them scaled the sheet to 43%, present but unreadable; (3) `fitScaleToPane` scales the sheet to whatever pane remains, so it is never clipped again. Verified across nine real device widths: every one now lands between 0.60 and 1.00 scale (worst case ~478 CSS px of sheet) where iPad portrait was previously clipped outright. **The subtle part was which layout path tablets take.** The obvious fix — send them down the existing phone branch — was wrong twice over: that branch skips Paged.js and relies on `html.is-mobile` CSS to reveal the iframe, so on a tablet the pane would have gone **permanently blank** (iframe stays `visibility:hidden`), and its height is measured before pagination, so multi-page documents would clip. Tablets therefore take the desktop path — Paged.js runs, the poll waits for the page count to settle, the frame is revealed — and scaling is applied to that settled result, which also keeps on-screen page breaks matching the PDF (see [PAGINATION.md](PAGINATION.md)). Caught in review, each verified against the real files before fixing: the portrait `@media (max-width: 900px)` block was **unscoped, and phones match it too** — it would have positioned the phone meeting list off-screen with no way back, since the phone rules override only `display`/`width` and never `position`/`transform`; the tablet `.paper { max-width: none }` override sat *above* the 860px base rule at equal specificity and so never applied; the dismiss-scrim was not excluded from Timeline, which hides the list, the ☰ and the scrim's only dismiss routes, stranding a dark layer that ate the next click; entering Timeline from the sidebar (exempt from the outside-click handler) stranded `.list-open` the same way; `openList()` fired at every non-phone width, arming an overlay that would spring open on a later resize; and the wide-pane reset left a stale `frame.style.height` that Paged.js never re-measures. Covered by three checks kept with the change: a device-width table, a CSS cascade/scoping audit (including "no unscoped pane selector"), and a behavioural test of the scaler. **Confirmed working on the real iPad Air and iPad Pro** by the user after deploy. Two follow-ups found while porting this to the React mirror and fixed in both (@220): opening a meeting from a Timeline dot leaves the Timeline project selected, so `.timeline-mode` persisted on the detail view and hid the list AND its ☰ toggle — that screen became a dead end, now keyed off a narrower `.timeline-only` (timeline showing, no meeting open); and the 128px indent that clears the toggle stayed applied when the toggle was hidden, wrapping the detail-bar buttons onto an extra row. Live @218, refined @220.

- **2026-08-29** — **Per-project access is now by named email, and the access panel is a full page.** Previously a project was all-or-nothing: 🔓 Public (anyone with the link) or 🔒 Locked (admins and editors only). There was no way to say "these four people may see this project". The backend had carried `PROJECT_ACCESS`, `canSeeProject_`, `addProjectViewer` and `removeProjectViewer` for some time, but **no UI ever wrote to them and no read path ever called `canSeeProject_`** — `listMeetings`/`searchMeetings`/`getMeeting` all gated purely on the per-row `visible` flag, so the entire per-email ACL was dead code that this CHANGELOG nonetheless described as a working feature. Adding the UI alone would have shipped a control that granted nothing. Fixes: (1) `canSeeProject_` rewritten to the intended rule — public ⇒ everyone, locked ⇒ admins, editors and named emails only, explicitly **not** the whole staff domain (`rule.domain` survives as an opt-in that is off unless set); (2) that gate threaded into every read path — `listMeetings`, `searchMeetings`, `getMeeting`, both bootstrap builders' sidebar counts, and `addComment` so nobody can post into a project they cannot read — each now a two-gate check, the per-meeting `visible` switch **and** the per-project guest list; (3) `getMeeting` gated too, or a locked project would have stayed one shared link away from anybody; (4) projects the viewer cannot see are omitted from the sidebar rather than sent with `canSee:false`, which would have advertised exactly the set of projects someone is being kept out of. **Identity was the subtlety:** these paths read `googleEmail_()`, which is `''` for every visitor under `ANYONE_ANONYMOUS` — gating on it would have hidden locked projects from the very people named on them, so they now use `identify_(token)` (the same trap as the 2026-08-20 editor sign-in fix). `emailHasAnyAccess_` deliberately does **not** reuse `canSeeProject_`: that now returns true for a public project whoever is asking, which would have made every address on earth "have access" and turned the sign-in form into an open mail relay — it checks named/editor/admin access only. On the UI side the panel moved from a 798px dialog to a full-page workspace with a pinned header, Projects/Editors tabs, and a filter matching project names **and** addresses (so "what can nattapong@ see?" is one search); each project card carries its own guest list as removable chips, accepts a pasted list (commas/semicolons/spaces/newlines, rejecting the whole batch on a typo rather than half-saving), and can copy its list onto other locked projects. **Note the migration:** no locked project had named emails yet, so on this deploy they became admin/editor-only until people are added — chosen deliberately over grandfathering staff access, with a standing banner in the panel while any project is in that state. Caught in review: two regexes lost their backslashes to shell escaping (`/[s,;]+/` would not have split on spaces, and would have rejected any address containing the letter "s"), `removeComment` kept `googleEmail_()` while `addComment` moved to `identify_` — leaving a PIN-signed editor able to post a comment but never delete it — and Esc in the "Copy to…" prompt closed the whole panel behind it. Live @217.

- **2026-08-20** — **Editors can finally sign in (email + password).** Employees added to `EDITOR_EMAILS` had no ✎ Edit button and no way to get one. Root cause: the deployment is `ANYONE_ANONYMOUS` + `USER_DEPLOYING`, so Google hides every visitor's email from the script — `Session.getActiveUser().getEmail()` returns `''` for everyone except the deploying owner. `isEditorEmail_('')` is always false, so the allow-list could never match anyone and the button never rendered. Worse, `identify_(token)` **ignored its token argument** and returned `googleEmail_()` unconditionally, so even a valid session resolved to nobody. Fixes: (1) `identify_` now actually consults the session token; (2) a real login — each editor has an account (`editorLogin`), created by an admin via Settings → 🔐 Project access → Editors → **Set password**, with the employee forced to choose their own on first sign-in (`mustChange`) so the admin does not go on knowing it; (3) the ✎ Edit button is shown to **everyone**, with identity demanded on click rather than for viewing, so an editor can see the way in before proving who they are; (4) `getSessionState` resolves via `identify_`, so a reload does not forget them. Passwords are stored salted and iteratively hashed in `EDITOR_CREDS`, never in plaintext; wrong email and wrong password return the same error (no oracle for discovering who has edit access); 8 failures lock that email for 15 minutes; and authorisation is re-checked at login, so removing someone takes effect immediately. Covered by a 39-case suite run against the real `Auth.js`. **The work factor had to be measured, not assumed:** Apps Script has no PBKDF2/bcrypt, and `Utilities.computeDigest` costs ~1ms per call — 12000 rounds took **11.8 seconds** per login on the live deployment, so the count is 1200 (~0.85s). Each credential stores its own round count, so tuning it never locks out existing users. **Caught during review:** because `isAdmin_` called `identify_`, this would have let an editor account on an `ADMIN_EMAILS` address mint a full-admin session and bypass `ADMIN_PASSWORD` entirely — verified as a live exploit against the real code, then closed by pinning admin to the Google session or an explicit password login. Also threaded a request-scoped actor through the editor write paths so the audit log records the real person instead of `(anonymous)`. Live @208.
- **2026-08-20** — **Fixed screen-vs-PDF page-break drift, and dated PDF filenames.** `@page` never declared a page `size`, so the two engines that paginate this document each chose their own: Paged.js (the on-screen preview) used its default, while Chrome's print engine used whatever the **print dialog's destination** was set to. A4 is 18mm taller than US Letter — ~68px more content per page — so on an A4 destination every item slid one page earlier than the screen showed (reported as item 4.4 ending page 2 in the PDF where the screen ended at 4.3). The same document therefore paginated differently on differently-configured machines. Compounding it, the layout was built around Letter (`body{max-width:816px}` = 215.9mm) while the surrounding comments claimed A4 — the contradiction that let this survive the earlier pagination work. Fixes: (1) `@page{size:A4;margin:2.7cm 17mm 2cm}` — all four margins explicit, so neither engine defaults anything; (2) all geometry moved off `body` onto `@page`, because Paged.js applies `body` padding *inside* its own page-margin box while Chrome does not (the screen's text column was 64px narrower, re-wrapping every paragraph), and `padding-bottom:100px` was reserved by Paged.js on every page but applied by Chrome only once; (3) fragmentation rules stated explicitly (`break-after:avoid` on headings, `orphans/widows:3` — at the CSS default of 2 a four-line paragraph may split 2+2, which Chrome does and Paged.js does not). The editor's `.ed-area` was still on Letter geometry and now matches (`210mm`, `2.7cm 17mm 2cm`). Also fixed a pre-existing bug in `buildEditorPageCss_()` where the `@media print` strip regex matched only one nested rule, leaving a stray `}` at the end of the editor's stylesheet. Verified by rendering both ways and reading the real PDF back page-by-page: **0/30 blocks agreed before on an A4 destination → 30/30 after**, across A4, Letter and CSS-size destinations; 45/46 on realistic Thai/list/table content; 1077/1080 (99.7%) over 24 generated documents. Known residual: a block landing within a few pixels of a page boundary can still differ (Chrome tolerates slight overflow where Paged.js does not) — engine rounding, not a stylesheet value; four attempts to close it failed or regressed, documented in [PAGINATION.md](PAGINATION.md) so it is not chased again. Separately, exported PDFs now carry the meeting date in the filename (`VCB Meeting Minutes 18.8.69`) — every export was previously named identically and indistinguishable in a folder. Also removed a 48px pad the reading iframe was adding to its own height — introduced as clipping insurance during the Paged.js work, it rendered as a bare white strip between the last sheet and the attachments card, since the document already ends with 22px of its own padding; verified across 1–4 page documents with webfonts loading late that nothing clips and no inner scrollbar appears without it. React mirror synced; `OVERRIDE_CSS` verified byte-identical between GAS and React. Live @204.

- **2026-08-19** — **Page-accurate rendering across all three views.** The reading view, Print/PDF and the editor now break pages in exactly the same places. The reading view runs [Paged.js](https://pagedjs.org/) in its preview iframe, so page boundaries come from a real implementation of CSS Paged Media rather than a height calculation — the previous JS approximation could not reproduce widows/orphans or `break-after: avoid`, so a heading sat on page 1 on screen but page 2 in the PDF.
