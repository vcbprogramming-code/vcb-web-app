# HR Work Log — เอกสารข้อกำหนดฟังก์ชัน (Functional Specification)

> เอกสารนี้อธิบายการทำงานของโมดูล **HR Work Log** (บันทึกการทำงานรายวัน) ตามที่ implement จริงใน React/Express
> ที่ `hr-worklog/src/` และ `api/src/routes/hr.js` ภายใต้ VCB Connect ไม่ใช่เอกสารออกแบบในอุดมคติ —
> ทุกพฤติกรรมที่กล่าวถึงอ้างอิงจากโค้ดจริงที่มีอยู่ในระบบ ณ วันที่จัดทำเอกสาร

---

## 1. ภาพรวมของโมดูล

HR Work Log คือระบบบันทึกการทำงานรายวัน (attendance / manday logging) สำหรับพนักงานหน้างานก่อสร้างของ
VCB จำนวนประมาณ **345 คน** กระจายอยู่ใน **8 โครงการก่อสร้าง (sites)** เช่น บางตุ้ย, บางหว้า, พุทธมณฑล,
สาย 5, สุพรรณบุรี ฯลฯ โมดูลนี้เดิมเป็น Google Apps Script ที่ทำงานบน Google Sheet (ดูโค้ดต้นฉบับที่
`../ORIGINAL CODE/Code.gs`) และถูกพอร์ตมาเป็นเว็บแอป React 18 + Vite + Tailwind (front-end) คุยกับ
Express API (`api/src/routes/hr.js`) ที่ต่อกับฐานข้อมูล PostgreSQL schema `hr`

หน้าที่หลักของระบบคือ:

- ให้ผู้ควบคุมงานหรือ HR **กรอกงานประจำวัน** ของพนักงานแต่ละคนในแต่ละไซต์ (หน้า **Entry**)
- ให้ผู้บริหาร/ผู้จัดการ **ดูภาพรวมความคืบหน้า** ของแต่ละไซต์ในแต่ละเดือน พร้อมสรุป manday และสัดส่วนกิจกรรม
  (หน้า **Dashboard**)
- จัดการ **คำขอลา (leave requests)** และดูทำเนียบพนักงาน (roster) ต่อไซต์ (หน้า **Requests**)
- แสดง **ดัชนีงานอ้างอิง** (กิจกรรม + รหัสต้นทุน ERP) ที่ใช้ประกอบการกรอกงาน (หน้า **Work Index**)
- ให้แอดมิน **จัดการโครงการ** (เปิด/ปิดไซต์) และตั้งค่าการแสดงผลส่วนตัว (หน้า **Settings**)

หน่วยนับที่สำคัญที่สุดในระบบคือ **manday** — หนึ่งคนทำงานหนึ่งวัน แม้จะกรอกงานสองช่อง (สองกิจกรรม) ในวันเดียวกัน
ก็นับเป็น 1 manday เท่านั้น ตัวเลขนี้มาจาก database view `hr.mandays` เพียงที่เดียว ไม่มีการนับซ้ำที่ front-end
(ดูหัวข้อ 4 กฎทางธุรกิจ)

## 3. รายละเอียดฟังก์ชันแต่ละหน้า

### 3.1 Dashboard (`src/Dashboard.jsx`)

**ทำอะไรได้:** แสดงการ์ดสรุปของแต่ละไซต์ (site card) ในเดือนที่เลือก มี 3 มุมมองสลับได้ผ่าน `Segmented`:

1. **Progress (ความคืบหน้า)** — วงแหวนเปอร์เซ็นต์ (ring) แสดงสัดส่วน manday ที่บันทึกแล้ว เทียบกับ manday
   ที่ "ควรจะบันทึกได้" ในเดือนนั้น พร้อมปฏิทินย่อ (`MiniCal`) ไล่สีตามสถานะของแต่ละวัน
2. **Top Activities** — บาร์ชาร์ตแบบ hand-written (div ธรรมดา ไม่ใช้ chart library ตาม `TECH_STACK.md`)
   แสดงสัดส่วนกิจกรรมที่ถูกกรอกมากที่สุดในไซต์นั้น
3. **Top Cost Codes** — เหมือนข้อ 2 แต่เป็นรหัสต้นทุน ERP

**Logic การทำงานโดยละเอียด:**

- ดึงข้อมูลผ่าน `getSummary({ year, month })` → `GET /api/hr/summary?year&month`
- `MiniCal` (บรรทัด 21-70): ไล่สีแต่ละวันของเดือนตามกฎ — วันนี้ = accent สี, วันหยุด (อาทิตย์) = สีเทา,
  วันในอนาคต (> พรุ่งนี้) = สีจาง, วันที่ยังอยู่ในช่วงแก้ไขได้ (`cutoff`..`ahead`) = สีเหลือง edit, วันที่ปิดแล้ว
  และมีคนกรอกครบ headcount = สีเขียว ok, ที่เหลือ = สีแดง miss ตัวเลข `filled` มาจาก `hr.mandays` view
  ผ่าน API เท่านั้น จึงนับ "คน" ไม่ใช่ "แถว" — พนักงานที่กรอกทั้งงานหลักและงานเสริมนับเป็น 1 ไม่ใช่ 2
- **การคำนวณ fill rate ของ ring (`SiteCard`, บรรทัด 190-210):** เป็นการคำนวณที่ **client คำนวณเอง**
  ไม่ใช่ server-computed — สูตรคือ `logged / (workdays × n_emp)` โดย `workdays` นับจากปฏิทินเฉพาะวันที่ผ่านมาแล้ว
  (ไม่รวมวันอาทิตย์) และ `n_emp` คือ headcount **ปัจจุบัน** ของไซต์ ข้อจำกัดตรงนี้คือถ้า roster
  เปลี่ยนกลางเดือน (มีคนเข้า/ออกไซต์) ตัวหารจะไม่ถูกต้อง 100% (ดูข้อจำกัดข้อ 3 ในหัวข้อ 6)
- **ปุ่มดาวน์โหลดรายงาน manday** (`onExport`): เรียก `exportMandayReport({ year, month })` โดยส่งออก
  **เดือนที่หน้าจอกำลังแสดงอยู่ ณ ขณะนั้น** ไม่ใช่เดือนปัจจุบันของปฏิทิน — มีคอมเมนต์เตือนในโค้ดว่านี่คือจุดที่
  พลาดง่ายเมื่อผู้ใช้เลื่อนเดือนไปมา แล้วลืมว่าตัวเองไม่ได้อยู่ที่เดือนปัจจุบันแล้ว
- `hidden` (ไซต์ที่ถูกซ่อนต่อเครื่อง จาก `usePrefs()`) กรองออกที่ layer นี้เท่านั้น เป็นการซ่อนเพื่อความสะดวก
  ไม่ใช่การจำกัดสิทธิ์ — สิทธิ์จริงถูกบังคับที่ API

### 3.2 Entry — หน้ากรอกงาน (`src/Entry.jsx`, `CoverageGrid.jsx`, `WeekGrid.jsx`, `Picker.jsx`)

หน้านี้คือหัวใจของโมดูล มี **สองมุมมอง (view)** ของข้อมูลเดือนเดียวกัน สลับกันด้วย `Segmented`:

#### 3.2.1 Coverage view (`CoverageGrid.jsx`) — ภาพรวมทั้งเดือน อ่านอย่างเดียว

- ตารางแนวนอน 1 แถวต่อพนักงาน, 1 คอลัมน์ต่อวัน (สูงสุด 31 คอลัมน์) ขนาดเซลล์ตายตัว 34px จำลองขนาดจาก
  แอปต้นฉบับ (Google Sheet) เป๊ะ ๆ
- แต่ละเซลล์แสดงรหัสกิจกรรม (หรือสองรหัสถ้ามีทั้งงานหลัก+งานเสริมและไม่ซ้ำกัน) สีพื้นบอกสถานะวัน: today,
  weekend (เสาร์ทำงานปกติ อาทิตย์เท่านั้นที่หยุด), future, editable, ok (กรอกครบ), miss (ยังไม่กรอก)
- **แถบสรุปรายวัน (day strip)** ด้านบนตาราง แสดง % ความครบถ้วนของแต่ละวัน (จำนวนคนที่กรอกแล้ว/ทั้งหมด)
- **ตัวไฮไลต์รหัสกิจกรรม (🔦 highlighter)**: เลือกได้หลายรหัสกิจกรรมจาก dropdown แล้วเซลล์ที่ตรงกันจะคง
  ความชัด ส่วนที่เหลือจางลง (`opacity-[.24]`) ค่านี้ถูกเก็บไว้ใน `localStorage` (`hr_covhl`) ต่อเครื่อง
  ให้คงอยู่แม้ reload
- **การคลิกเซลล์ = jump ไปหน้า Weekly**: กริดนี้เป็น **read-only โดยตั้งใจ** — ตารางแน่นเกินกว่าจะเปิด picker
  ในนั้นได้ (31 คอลัมน์) การคลิกเซลล์ที่กรอกแล้วหรืออยู่ในช่วงแก้ไขได้จะเรียก `onJump(eid, date)` ซึ่งใน
  `Entry.jsx` (ฟังก์ชัน `jump`) จะเลื่อน `weekStart` ไปยังสัปดาห์ที่มีวันนั้น, ตั้ง `focus` ไปที่คนและวันนั้น,
  แล้วสลับ `mode` เป็น `'week'` โดยอัตโนมัติ

#### 3.2.2 Weekly view (`WeekGrid.jsx`) — แก้ไขได้จริง, ครั้งละ 7 วัน

- แสดงทีละสัปดาห์ (7 วัน) เพื่อให้มีที่ว่างพอสำหรับเปิด picker ในแต่ละเซลล์ มีปุ่มเลื่อนสัปดาห์ก่อนหน้า/ถัดไป
- **แต่ละวันมี 2 ช่อง (slot) เรียงซ้อนกันในแนวตั้ง** — นี่คือกฎสำคัญที่สุดของระบบ:
  - **Slot 1 = งานหลัก** แสดงเสมอ เป็น field `team` (สำหรับพนักงานที่ `kind === 'operation'`) หรือ `detail`
    (สำหรับ `support`) — ตัดสินโดยฟังก์ชัน `primaryField(kind)` ใน `lib/cells.js`
  - **Slot 2 = งานเสริม** (optional) แสดงเป็น "+ งานที่ 2" เมื่อยังว่าง field คือ `pm`
  - **"Slot" ไม่ใช่ช่วงเวลาของวัน** — field ชื่อ `pm` มาจากชื่อคอลัมน์ในสเปรดชีตเดิม ("AM N"…"PM N")
    ซึ่งเป็นชื่อทางประวัติศาสตร์เท่านั้น **ไม่มี UI string ไหนในโมดูลนี้ระบุว่าเป็นเช้า/บ่าย** — มี unit test
    ยืนยันว่าพจนานุกรมคำแปลไม่มีคำว่า เช้า/บ่าย เลย ทั้งฝั่ง front-end (`lib/cells.js` comment) และฝั่ง
    backend (`api/src/routes/hr.js` comment) ย้ำกฎนี้ตรงกัน
  - ช่องที่ 2 จะถูก**ซ่อนด้วย `invisible`** (ไม่ใช่ unmount) เมื่องานหลักยังว่างและช่องเสริมก็ว่าง — เหตุผลคือ
    ถ้า unmount ออกไปเลย ความสูงของทุกแถวจะเปลี่ยนทันทีที่ช่องแรกถูกกรอก ทำให้ตารางทั้งตารางเด้ง reflow
    ทุกครั้งที่บันทึก (แถวอื่น ๆ ที่ไม่เกี่ยวก็จะขยับตาม) การใช้ `invisible` (คง layout box ไว้แต่ไม่วาดและ
    ไม่รับคลิก) แก้ปัญหานี้
  - การกรอกทั้งสองช่องยังนับเป็น **1 manday เท่านั้น** — ไม่มีการแสดงตัวเลข manday ต่อเซลล์ในกริดนี้เลย
    ตัวเลขอยู่ที่ Dashboard เท่านั้นซึ่งอ่านจาก `hr.mandays` view
- **การล็อกเซลล์ตาม edit window**: `locked = day.date < cutoff || day.date > ahead` เป็นเพียง **UI hint**
  เพื่อไม่ให้เปิด picker ในเซลล์ที่ server จะปฏิเสธแน่ ๆ — กฎจริงบังคับที่ database trigger
  `enforce_entry_window` และ API แปลงเป็น HTTP 403 `OUTSIDE_EDIT_WINDOW`
- **ป้ายคำขอลาที่อนุมัติแล้ว**: ถ้า `note` ของวันนั้นขึ้นต้นด้วย `[LV]` (parse โดย `parseLeaveNote()` ใน
  `lib/cells.js`) จะแสดง badge "✓ [ประเภทการลา]" ใต้เซลล์ — จำเป็นเพราะการอนุมัติคำขอลาจะเขียนรหัส Z-2
  (ลา) แบบเดียวกับที่ HR พิมพ์มือทุกประการ (byte-identical) จึงต้องมี marker นี้เพื่อแยกแยะว่าวันนั้นมาจาก
  การอนุมัติคำขอลาจริง ไม่ใช่คนพิมพ์เอง

#### 3.2.3 ตัวเลือกกิจกรรมแบบ 2 ขั้นตอน (`Picker.jsx`)

เมื่อคลิกเซลล์ที่แก้ไขได้ จะเปิด popup ลอย (positioned ตาม anchor ของเซลล์ที่คลิก, พลิกขึ้น-ลงอัตโนมัติ
ตามพื้นที่ว่างบนจอ):

- **ขั้นที่ 1 — กิจกรรม (Activity)**: เลือกจากรายการ "master work index" จัดกลุ่มตาม `category`
  รองรับค้นหาด้วยข้อความ (`query`) แต่ละรายการมีจุดสีบอก mapping:
  - จุดเขียว = `one-to-one` (มีต้นทุนคงที่ในตัว จบที่ขั้นตอนเดียว)
  - จุดเหลือง = `one-to-many` (ต้องเลือกหมวดงานต่อในขั้นที่ 2)
- **ขั้นที่ 2 — หมวดงาน (Work Category / รหัสต้นทุน ERP)**: ปรากฏเฉพาะกรณี `one-to-many` เท่านั้น
- **ค่าที่บันทึกจริงในเซลล์เป็น string ผสม**: `"<รหัสกิจกรรม> / <รหัสต้นทุน>"` เช่น `"A-1 / 5"` — นี่คือ
  string เดียวกับที่สเปรดชีตเดิมเก็บ และเป็น string ที่ backend ใช้ `split_part(value, ' / ', ...)` ในการ
  แยกวิเคราะห์เพื่อสร้างสรุป Top Activities/Top Cost Codes บน Dashboard — **ถ้าเปลี่ยนตัวคั่น " / " ในโค้ด
  Picker.jsx จะทำให้รายการสรุปทั้งสองฝั่งว่างเปล่าทันที**
  - กิจกรรมกลุ่ม Z (Z-1 Standby / Z-2 Leave / Z-3 Resignation) เป็น `one-to-one` แต่**ไม่มีต้นทุนคงที่**
    (ไม่มี `fixed_cost`) จึงบันทึกเป็นรหัสเปล่า ๆ (`"Z-2"`) โดยไม่ต่อ `" / "` เพื่อไม่ให้ค่ากลายเป็น
    `"Z-2 / "` ซึ่งจะทำให้ `split_part` บน dashboard พัง
- **ปุ่ม "Clear" (ล้างค่า)**: กดแล้วเรียก `onApply('')` ทันที ซึ่งจะไปลบข้อมูลในเซลล์ (ดูหัวข้อ "empty
  value deletes" ในกฎทางธุรกิจ)
- **Escape ที่ขั้นตอน 2 จะย้อนกลับไปขั้นตอน 1** ไม่ใช่ปิด popup ทันที — คอมเมนต์ในโค้ดระบุว่านี่คือ
  ปัญหาที่ถูกร้องเรียนบ่อยที่สุดในเวอร์ชันสเปรดชีตเดิม (เสียกิจกรรมที่เพิ่งเลือกไปเพราะอยากเปลี่ยนแค่หมวดงาน)

**บั๊ก outside-click และ capture-phase fix (คอมเมนต์ในโค้ดยังบันทึกไว้ครบ):**

`Picker.jsx` บรรทัด 66-105 มีคอมเมนต์อธิบายบั๊กที่เคยเกิดขึ้นอย่างละเอียด — เดิมทีปุ่มรายการกิจกรรมประเภท
`one-to-many` (จุดสีเหลือง) **คลิกไม่ติด** หรือคลิกแล้ว popup ปิดไปเฉย ๆ แทนที่จะเลื่อนไปขั้นที่ 2 สาเหตุคือ:
เมื่อคลิกไอเทมที่เป็น one-to-many, `onMouseDown` เรียก `pick(it)` ซึ่งเรียก `setStep(2)` เป็น synchronous
state update ภายใน discrete DOM event handler — React 18 จะ flush แบบ synchronous ทันที (ไม่ batch)
ทำให้ re-render แทนที่รายการขั้นที่ 1 ด้วยขั้นที่ 2 (data/keys ต่างกัน) — DOM node เดิมที่เป็นเป้าหมายคลิก
ถูกลบออกจากเอกสารไปแล้ว **ก่อนที่** event listener แบบ bubble-phase บน `document` จะทำงาน ทำให้เมื่อถึงเวลา
เช็ค `.contains()` node เป้าหมายไม่อยู่ใน DOM แล้วเลย (ไม่ใช่แค่ไม่อยู่ใน `boxRef` แต่ไม่อยู่ใน DOM ใด ๆ เลย)
`.contains()` จึงตอบ `false` อย่างถูกต้องตามข้อมูลที่มันเห็น แต่คำถามมาถึงช้าเกินไป

**วิธีแก้ที่ใช้จริง**: เปลี่ยน listener `mousedown` บน `document` ให้ทำงานที่ **capture phase**
(`document.addEventListener('mousedown', onDown, true)`) แทน bubble phase — capture phase ทำงาน "ขาลง"
ก่อนที่ React จะ dispatch synthetic bubble-phase event และก่อนที่ node จะถูกลบออก จึงเห็น DOM ตามสภาพจริง
ขณะที่เมาส์กดลงจริง ๆ เสมอ

โค้ดยังมี "belt-and-suspenders" อีกชั้น: `onClose` ถูกอ่านผ่าน `onCloseRef` (ref) แทนที่จะเป็น dependency
ตรงของ `useEffect` เพราะ `Entry.jsx` re-render เกือบทุก keystroke/save (จาก `entries`, `flash` state) —
ถ้า caller ส่ง inline arrow function `() => setPicker(null)` เป็น prop จะได้ reference ใหม่ทุกครั้ง ทำให้
effect นี้ teardown/reattach listener ซ้ำ ๆ ซึ่งอาจไปตกตรงกลางระหว่าง mousedown ของ step 1 กับ React
dispatch ของมันเอง ทำให้กลืนคลิกที่ควรจะเลื่อนไป step 2 ไปเฉย ๆ ดังนั้น `Entry.jsx` จึงจงใจสร้าง
`closePicker` ด้วย `useCallback` ให้เป็น reference คงที่ (`const closePicker = useCallback(() => setPicker(null), [])`)

#### 3.2.4 การบันทึก/ล้างค่าเซลล์ (`Entry.jsx` → `applyCell`)

- **ไม่มีปุ่ม Save** — การบันทึกเกิดขึ้นทันทีต่อเซลล์ (per-cell, immediate) เลียนแบบพฤติกรรมสเปรดชีตเดิมที่
  เซลล์ถูกบันทึกทันทีที่พิมพ์เสร็จ
- **Optimistic UI update**: เมื่อผู้ใช้เลือกค่าจาก Picker, `applyCell(eid, date, field, value)` จะ
  อัปเดต state `entries` ทันที (ก่อนรอ response จาก server) เพราะกริดมีความหนาแน่นสูง การรอ round-trip
  ทุกคลิกจะรู้สึกหน่วง
- จากนั้นเรียก `saveCells({ site, cells: [{ eid, date, slot: slotOf(field), value: trimmed || null }] })`
  → `POST /api/hr/cells`
- **หาก API ปฏิเสธ (catch)**: `setEntries(before)` — **rollback กลับไปที่ state ก่อนหน้าทั้งหมด**
  แล้วแสดงข้อความแจ้งเตือนตามประเภทของ error:
  - ถ้าเป็น `OUTSIDE_EDIT_WINDOW` → แสดงด้วยโทนสี **warning (เหลือง)** ไม่ใช่สีแดง เพราะนี่คือกฎธุรกิจที่
    ทำงานถูกต้องแล้ว ไม่ใช่บั๊ก และค้างอยู่บนจอจนกว่าจะมี action ถัดไป (ไม่หายเองใน 1.8 วินาที)
  - ข้อผิดพลาดอื่น ๆ → แสดงด้วยโทน **error (แดง)**
- ถ้าบันทึกสำเร็จ → flash สีเขียว "บันทึกแล้ว ✓" หรือ "ล้างแล้ว" (หายเองใน 1.8 วินาที)
- **ทำไม empty value = ลบ ไม่ใช่บันทึกเป็นค่าว่าง**: `trimmed = String(value || '').trim()` — ถ้า
  `trimmed` เป็นค่าว่าง จะส่ง `value: null` ไปยัง API ซึ่ง backend จะรัน `DELETE FROM hr.work_entries`
  แทนที่จะ `INSERT` ค่าว่าง เหตุผลคือถ้าเก็บเป็นแถวว่าง (`''`) แถวนั้นก็ยังนับว่า "มีอยู่" และ
  `hr.mandays` view จะนับวันนั้นเป็นวันที่ทำงานผิดพลาด — ทั้งฝั่ง optimistic update ใน `applyCell` และ
  ฝั่ง backend (`router.post('/cells', ...)`) ทำแบบเดียวกันคือ ลบ field ออกจาก object แทนที่จะตั้งเป็น `''`
- **หมายเหตุเรื่อง note**: ถ้าเซลล์สูญเสีย slot สุดท้ายไปแล้ว (ทั้งสอง slot ว่าง) แต่ยังมี `note` อยู่
  โค้ด optimistic update จะ**เก็บ note ไว้** เพราะ note เป็นของ "วัน" ไม่ใช่ของ "slot" ใดคนหนึ่ง

### 3.3 Requests — คำขอลาและทำเนียบพนักงาน (`src/Requests.jsx`)

**ทำอะไรได้:**

- **ฟอร์มยื่นคำขอลาใหม่** (ฝั่งซ้าย): เลือกไซต์ → โหลดทำเนียบพนักงาน (`getRoster(site)` →
  `GET /api/hr/sites/:siteKey/roster`) → เลือกชื่อพนักงาน → เลือกประเภทการลา (`LEAVE_TYPES`:
  sick/personal/vacation/maternity/ordination/other) → กำหนดช่วงวันที่ (วันสิ้นสุดจะตามวันเริ่มต้น
  โดยอัตโนมัติถ้ายังไม่ได้ตั้ง เพื่อรองรับกรณีลา 1 วันซึ่งเป็นกรณีส่วนใหญ่) → ระบุเหตุผล (ไม่บังคับ) → ส่ง
- **รายการคำขอ 3 แท็บ** (ฝั่งขวา, ใช้ endpoint เดียวกัน `listLeave()` กรองต่างกัน):
  1. **My Requests (ของฉัน)** — ต้องเลือกพนักงานก่อนถึงจะเห็น; ยกเลิกได้ขณะที่ยัง `pending`
  2. **Pending Approval (รออนุมัติ)** — เห็นเฉพาะ admin/manager (`canDecide`); มีปุ่ม อนุมัติ/ปฏิเสธ
  3. **Decision History (ประวัติการตัดสินใจ)** — เห็นเฉพาะ admin/manager; กรองย่อยได้ทั้งหมด/อนุมัติ/ปฏิเสธ
     (ไคลเอนต์กรองจาก field `status !== 'pending'` เอง เพราะ API ไม่มี status `decided` โดยตรง)

**Logic สำคัญ:**

- คำขอลาแบบร่างจะยกเลิกได้เฉพาะตอนที่ยัง `pending` เท่านั้น — เมื่อถูกตัดสินใจแล้ว (approved/rejected)
  แถวนั้นถือเป็น "บันทึกถาวร" ไม่ใช่ draft อีกต่อไป ปุ่มยกเลิกจึงหายไป
- **409 ALREADY_DECIDED**: เมื่อมีผู้จัดการสองคนพยายามอนุมัติ/ปฏิเสธพร้อมกัน ฝั่งที่มาทีหลังจะได้ 409
  กลับมา ระบบแปลความว่า "ไม่ใช่บั๊ก แค่มีคนตัดสินใจไปก่อนแล้ว"
- แสดงข้อความ "showing N/M" เมื่อรายการประวัติถูกจำกัดจำนวน (server cap ที่ 200 rows default,
  สูงสุด 500) เพื่อไม่ให้ผู้ใช้เข้าใจผิดว่ารายการที่เห็นคือทั้งหมด

### 3.4 Work Index — ดัชนีงานอ้างอิง (`src/WorkIndex.jsx`)

**ทำอะไรได้:** แสดงตาราง 2 แท็บ (read-only ทั้งหมด):

1. **กิจกรรม (Activity)** — รหัส, ชื่อ, หมวดหมู่, และ mapping (1:1 พร้อมต้นทุนคงที่ หรือ 1:N)
2. **หมวดงาน (Cost Code)** — รหัส, ชื่อไทย, ชื่ออังกฤษ (Work Category)

รองรับค้นหาด้วยข้อความ (filter ฝั่ง client จาก `activities`/`costs` ที่แคชไว้ใน `HrData.jsx` ตั้งแต่แรกโหลด
แอป, ไม่มีการเรียก API ซ้ำ) หน้านี้เป็น **read-only ทั้งหมด** — การแก้ไขข้อมูลอ้างอิง (`PUT
/api/hr/index/activity`) มี wrapper ใน `lib/hrApi.js` แต่ไม่มี UI เพราะเครื่องมือแก้ไขในสเปรดชีตเดิมเป็นแบบ
paste-from-Excel bulk import ซึ่งจงใจไม่พอร์ตมา

### 3.5 Settings — การตั้งค่า (`src/SettingsPage.jsx`)

**ทำอะไรได้ (แบ่งเป็น 4 ส่วน):**

1. **การแสดงผล** (ทุกคน): ธีม (light/dark/auto — ใช้ร่วมกันทั้งพอร์ทัล), ภาษา (ไทย/EN — ใช้ร่วมกันทั้ง
   พอร์ทัล), รูปแบบปี (พ.ศ./ค.ศ. — เฉพาะโมดูลนี้), มุมมอง dashboard เริ่มต้น, รูปแบบการแสดงเซลล์ (รหัส/ชื่อเต็ม)
2. **จัดการโครงการ** (เฉพาะ admin, component `ProjectsAdmin`): เปิด/ปิดโครงการ (`setSiteActive`),
   เพิ่มโครงการใหม่ (`addSite`) — คีย์ไซต์ (site key) ถูก derive อัตโนมัติจากชื่อโครงการผ่าน `siteKeyFrom()`
   (แปลงเป็น ASCII ตัวพิมพ์เล็ก, ถ้าไม่มี ASCII เลยจะ fallback เป็น hash ของชื่อ) ไม่ให้ผู้ใช้พิมพ์เองเพราะ
   คีย์นี้เป็น id ถาวรที่ผูกกับทุก entry ในฐานข้อมูล การปิดโครงการจะ**เตือน** จำนวนพนักงานที่ยังผูกอยู่กับ
   โครงการนั้น (ไม่บล็อก เพราะโครงการมักจบก่อนที่ HR จะย้ายคน)
3. **ไซต์ที่มองเห็นบน Dashboard** (ทุกคน): ซ่อน/แสดงไซต์ต่อเครื่อง (`localStorage`, ไม่ใช่ต่อบัญชี) — เป็น
   preference ความสะดวก **ไม่ใช่** การควบคุมสิทธิ์ (แยกจากการปิดโครงการของ admin โดยสิ้นเชิง — คอมเมนต์ในโค้ด
   ระบุว่าเคยมีเหตุการณ์ผู้จัดการไซต์เข้าใจผิดว่ากดซ่อนคือการปิดโครงการทั้งบริษัท)
4. **ระบบ**: แสดงค่า `LOCK_DAYS` เป็น **read-only** (ไม่มี input ให้แก้) เพราะค่านี้ถูกบังคับใช้ที่ database
   trigger สำหรับทั้งบริษัท ไม่ใช่ preference ของผู้ใช้แต่ละคน — ไม่มี API route ให้เขียนค่านี้เลย
5. **เกี่ยวกับ**: เวอร์ชัน, อีเมลผู้ใช้, บทบาท (role), จำนวนไซต์ที่ดูแล

## 4. Data Flow — endpoint ที่แต่ละหน้าเรียก

ตารางนี้อ้างอิงจาก `PORT_NOTES.md` และยืนยันตรงกับ `lib/hrApi.js` / `api/src/routes/hr.js`:

| หน้าจอ | เรียก endpoint | ส่งคืนอะไร |
|---|---|---|
| ทุกหน้า (ครั้งเดียวตอนโหลดแอป, ใน `HrData.jsx`) | `GET /api/hr/bootstrap` | role, isAdmin, canEntry, sites ที่มองเห็นได้, lockDays |

| Dashboard (ปุ่ม export) | `GET /api/hr/export/mandays?year&month` | ไฟล์ .xlsx (สตรีมกลับเป็น Response ดิบ) |
| Entry | `GET /api/hr/month?site&year&month` | roster (employees), entries (eid→date→{team\|detail, pm, note}), lockDays |
| Entry (การบันทึกเซลล์) | `POST /api/hr/cells` | `{ ok, written }` — batch เดียวในหนึ่ง transaction |
| Requests | `GET /api/hr/sites/:siteKey/roster` | รายชื่อพนักงานสำหรับฟอร์มยื่นคำขอ |
| Requests | `GET /api/hr/leave?site&status&eid&limit` | `{ rows, total, shown }` |

| Requests (อนุมัติ/ปฏิเสธ) | `POST /api/hr/leave/:id/decide` | คำขอที่อัปเดตแล้ว หรือ 409 ALREADY_DECIDED |
| Requests (ยกเลิก) | `DELETE /api/hr/leave/:id?eid=` | `{ ok: true }` หรือ 409/403 |
| Work Index | ไม่เรียกใหม่ — ใช้ cache จาก `GET /api/hr/index` | — |
| Settings (admin) | `GET /api/hr/sites`, `POST /api/hr/sites`, `PATCH /api/hr/sites/:siteKey` | รายการโครงการ, สร้างใหม่, เปิด/ปิด |

**Endpoint ที่ wrap ไว้ใน `lib/hrApi.js` แต่ไม่มี UI เรียกใช้งานในหน้าจอปัจจุบัน** (เป็นส่วนหนึ่งของ contract
เผื่ออนาคต): `PUT /api/hr/index/activity`, `GET /api/hr/sites/:siteKey/employees`, `PUT /api/hr/employees`,
`GET /api/hr/mandays`, `POST|GET /api/hr/migrations`, `GET /api/hr/audit`, `GET /api/hr/export/site/:siteKey`,
`GET /api/hr/export/index`, `GET /api/hr/export/cost-index`

## 5. กฎทางธุรกิจที่สำคัญ (Business Rules)

### 5.1 Slot ไม่ใช่ช่วงเวลาของวัน

Slot 1 คือ **งานหลัก** (main task, แสดงเสมอ), Slot 2 คือ **งานเสริม** (extra work, ตัวเลือกเสริม)
ชื่อ field `pm` มาจากคอลัมน์สเปรดชีตเดิม ("AM 1"…"PM 31") ซึ่งเป็นชื่อทางประวัติศาสตร์เท่านั้น
**ไม่มีความหมายเชิงเวลาเช้า-บ่ายในระบบนี้เลย** — กฎนี้ถูกย้ำซ้ำในคอมเมนต์ทั้งที่ `lib/cells.js`,
`WeekGrid.jsx`, `Picker.jsx` และในไฟล์ backend `hr.js` (ระบุเป็น "TWO RULES THAT THE MONEY DEPENDS ON")

### 5.2 หนึ่งวันที่กรอกทั้งสอง slot ยังเป็นแค่ 1 manday

ไม่มีฟังก์ชันนับ manday อยู่ใน `lib/cells.js` เลยโดยตั้งใจ — ตัวเลข manday ทั้งหมดต้องมาจาก
`row.mandays` ที่ `GET /api/hr/summary` ส่งกลับมา ซึ่งอ่านจาก database view `hr.mandays` การนับจาก
จำนวนแถวใน `work_entries` โดยตรงจะทำให้ตัวเลข**พองเกินจริง**สำหรับไซต์ที่มีการกรอกงานเสริมบ่อย ๆ
(backend comment ยืนยันตรงกัน: "Counting work_entries rows as mandays double-counts every two-task day")

ข้อยกเว้นที่น่าสนใจคือ **รายงาน export มีการถ่วงน้ำหนัก (weighting)**: ที่ `GET /api/hr/export/mandays`
วันที่กรอกงานหลักเพียงอย่างเดียวนับ 1.0 manday ต่อกิจกรรมนั้น แต่วันที่กรอกทั้งงานหลักและงานเสริม
จะถ่วงน้ำหนักเป็น **0.5 ต่อกิจกรรม** (สูตร `1.0 / slots`) เพื่อให้ผลรวมยังคงเป็น 1 manday ต่อวันจริง
ไม่ใช่ 1.5

### 5.3 ค่าว่าง = ลบ ไม่ใช่บันทึกเป็นค่าว่าง

`Entry.jsx` ส่ง `value: null` เมื่อเคลียร์เซลล์ และ API จะ `DELETE` แถวนั้นแทนที่จะ `UPDATE` เป็น `''`
เพราะแถวที่เก็บค่าว่างไว้ก็ยังถือว่า "มีแถวอยู่" และ `hr.mandays` view จะนับวันนั้นเป็นวันทำงานผิดพลาด

### 5.4 403 OUTSIDE_EDIT_WINDOW คือกฎธุรกิจ ไม่ใช่บั๊ก

Database trigger ชื่อ `enforce_entry_window` (ปฏิเสธด้วย SQLSTATE `42501`) บังคับว่า:

- ไม่มีใครกรอกล่วงหน้าเกิน **1 วัน** ข้างหน้าจากวันนี้ได้
- ผู้ใช้ที่ไม่ใช่ admin แก้ไขย้อนหลังได้ไม่เกิน **`LOCK_DAYS`** วัน (default 3 วัน, อ่านจาก `hr.config`)
- Admin ไม่มีข้อจำกัดด้านการย้อนหลัง

API (`rethrowWindow()` ใน `hr.js`) จับ error code `42501` แล้วแปลงเป็น HTTP 403 พร้อม
`code: 'OUTSIDE_EDIT_WINDOW'` ฝั่ง front-end (`errorMessage()` ใน `lib/errors.js`) แสดงข้อความนี้ด้วย
**โทนสีเหลือง (warning)** ไม่ใช่สีแดง (error) และระบุช่วงเวลาที่แก้ไขได้จริงให้ผู้ใช้เห็น เพื่อไม่ให้คนแจ้ง
IT ว่าระบบพังทั้งที่จริง ๆ กฎทำงานถูกต้องตามที่ออกแบบไว้ ข้อความนี้จะค้างอยู่บนจอจนกว่าจะมี action ถัดไป
(ไม่หายเองใน 1.8 วินาทีเหมือนข้อความสำเร็จทั่วไป) หน้า Weekly grid มี UI hint ล่วงหน้า (`locked`) เพื่อ
ไม่ให้เปิด picker ในเซลล์ที่รู้อยู่แล้วว่าจะถูกปฏิเสธ แต่นี่เป็นแค่การอำนวยความสะดวก ไม่ใช่การบังคับสิทธิ์จริง

### 5.5 ปีพุทธศักราช (Buddhist Era)

- ทุกวันที่ที่ผ่านไปมาระหว่าง client-server เป็น **Gregorian (ค.ศ.)** เสมอในรูปแบบ `yyyy-mm-dd`
- การแปลงเป็น พ.ศ. เกิดขึ้น **เฉพาะตอนแสดงผล** เท่านั้น: `useYear()` ใน `prefs.jsx` (`year + 543` เมื่อ
  ตั้งค่า `yearFmt === 'be'`) และฟังก์ชัน `gregorianToBe()` ที่ backend ใช้ตอนสร้างชื่อไฟล์รายงาน .xlsx
  (เช่น "HR Manday Report 2569-09.xlsx")
- การตั้งค่าปี (พ.ศ./ค.ศ.) เป็น **อิสระจากภาษาที่แสดงผล (ไทย/อังกฤษ)** โดยตั้งใจ — เหตุผลตามคอมเมนต์ใน
  `prefs.jsx`: เจ้าหน้าที่ HR อ่านเมนูภาษาไทยแต่ต้องกระทบยอดกับรายงาน ERP ที่ใช้ปี ค.ศ. อยู่บ่อยครั้ง
- `fromBuddhistLabel()` ใน `lib/dates.js` มีไว้แปลง label แบบ พ.ศ. (เช่น "2569-08") กลับเป็น Gregorian
  เฉพาะกรณีต้อง parse ป้ายชื่อจากสเปรดชีตเดิมเท่านั้น — API สมัยใหม่ส่งค่ากลับมาเป็น Gregorian อยู่แล้ว
  ทุกครั้ง

### 5.6 ไม่มีการนำเข้าข้อมูลย้อนหลังแบบ bulk (No bulk historical import)

จงใจไม่พอร์ตมาให้ ตรงกับหมายเหตุท้าย `api/src/routes/hr.js` — ตัวนำเข้าแบบ bulk ในเวอร์ชัน Apps Script
เดิมจะ timeout กลางทางเมื่อข้อมูลในชีตมีปริมาณมาก และ**ไม่รองรับการรันซ้ำ (not resumable)** การลองใหม่
จะเขียนข้อมูลบางเดือนซ้ำสองครั้งและข้ามบางเดือนไปเลย ข้อมูลย้อนหลังในระบบปัจจุบันถูกโหลดผ่าน one-off
migration script แยกต่างหาก ซึ่งหากล้มเหลวสามารถตรวจสอบและรันใหม่แบบควบคุมได้

### 5.7 วันหยุด — เสาร์ทำงาน อาทิตย์หยุด

`daysInMonth()` ใน `lib/dates.js` ถือว่ามีแค่วันอาทิตย์ (`dow === 0`) เป็นวันหยุด ตรงกับสเปรดชีตต้นแบบ
เพราะเป็นไซต์ก่อสร้างที่วันเสาร์ยังเป็นวันทำงานปกติ

## 6. ข้อจำกัดหรือสิ่งที่ยังไม่รองรับ

หมวดนี้คัดลอกและอธิบายจากส่วน **"What the UI wants that the API does not provide"** ใน `PORT_NOTES.md`
ทั้งหมด — สิ่งเหล่านี้เคยมีอยู่ใน mock data ของเวอร์ชันก่อนพอร์ต แต่ API จริง (`api/src/routes/hr.js`)
ยังไม่รองรับ แต่ละข้อถูก "ตัดออก" หรือ "ประมาณการทดแทน" อย่างจงใจ ไม่มีการปลอมข้อมูลขึ้นมาแสดง:

1. **การขาดงานรายบุคคล (`Employee.away`)** — mock เดิมทำเครื่องหมายวันที่พนักงานยังไม่ได้ย้ายเข้าไซต์
   (ทำให้เซลล์เป็นสีเทาแยกจาก "ยังไม่กรอก") แต่ `GET /api/hr/month` ไม่ส่ง field นี้กลับมาเลย ทำให้เซลล์
   เหล่านั้นแสดงเป็น "วันว่างธรรมดา" เหมือนวันที่ลืมกรอก ข้อมูลจริงมีอยู่ใน `hr.migrations` แต่ยังไม่มี
   endpoint ที่ project ข้อมูลนี้ลงบนกริดรายเดือน ผลคือพนักงานที่เพิ่งย้ายเข้าไซต์จะดูเหมือน "ขาดงาน" ในช่วง
   ก่อนย้ายมา ทั้งที่จริง ๆ ยังไม่เคยอยู่ที่ไซต์นั้นเลย ซึ่งทำให้ตัวเลขช่องว่าง (gap) บน coverage view
   ดูสูงเกินจริง

2. **`support_started` / `operation_started`** — Dashboard เวอร์ชันเก่าเคยแสดง "N จาก M คนได้บันทึกงาน
   อย่างน้อยหนึ่งวันแล้ว" แต่ `GET /api/hr/summary` ส่งกลับมาแค่ headcount และ mandays รวม ไม่มีจำนวน
   พนักงานที่ไม่ซ้ำกัน (distinct employee count) การ์ดนี้จึงถูก**ตัดออก** แทนที่จะประมาณการซึ่งอาจผิดพลาด

3. **Fill rate ที่คำนวณจาก server** — ฟิลด์ `fillRate`/`fillRateDenom` เดิมไม่มีใน response ของ
   `/summary` ปัจจุบัน วงแหวน (ring) บน Dashboard จึงถูก**คำนวณที่ `Dashboard.jsx` เอง** เป็น
   mandays ที่กรอกแล้ว หาร ด้วย (วันทำงานที่ผ่านไปแล้ว × headcount ปัจจุบัน) ทั้งสองส่วนมาจากตัวเลข
   manday ของ API จริง แต่**ตัวหารสมมติว่า headcount ปัจจุบันใช้ได้กับทั้งเดือน** ซึ่งจะคลาดเคลื่อนถ้า
   roster ของไซต์นั้นเปลี่ยนกลางเดือน หาก API มี field `denominator` ในแถวสรุปจะช่วยตัดการเดานี้ออกไปได้

4. **เครื่องหมายแก้ไขย้อนหลัง (Retro-edit markers, `SiteMonth.edits`)** — mock เดิมมีธงบอกว่าเซลล์ไหน
   ถูกแก้ไขภายหลังจากที่บันทึกครั้งแรก `GET /api/hr/audit` มีข้อมูลนี้อยู่จริง (เฉพาะ admin) แต่โครงสร้าง
   ข้อมูลไม่ได้จัดรูปแบบเป็น per-month-per-cell จึงยังไม่สามารถแสดง marker นี้บนกริดได้

5. **การเขียนค่า `LOCK_DAYS`** — หน้า Settings เดิมเคยมีช่องกรอกตัวเลขให้แก้ไขค่านี้ แต่ `hr.config`
   ไม่มี write route ให้เลย (ค่านี้ถูกบังคับใช้โดย database trigger สำหรับทั้งบริษัท) ค่าจึงแสดงเป็น
   **read-only** เท่านั้นในหน้า Settings

6. **ใบลาที่พิมพ์ได้ (printed leave slip)** — ยังไม่ได้พอร์ต `GET /api/hr/sites/:siteKey/roster`
   มีอยู่แล้วและส่ง identity fields ที่จำเป็นครบ แต่กฎการจัดวางหน้าเอกสาร (font ขนาด 10.5pt, grid
   ฟิลด์ 34mm/1fr, หน่วย mm/pt) ยังอยู่ใน `../ORIGINAL CODE/Code.gs` เท่านั้น ตาม `TECH_STACK.md`
   ควรสร้างฝั่ง server ด้วย PDFKit และฝังฟอนต์ Sarabun แทนการพิมพ์จาก browser โดยตรง

7. **การแก้ไขพนักงานและกิจกรรม (Employee and activity editing)** — `PUT /api/hr/employees` และ
   `PUT /api/hr/index/activity` มี wrapper ใน `lib/hrApi.js` แล้ว แต่**ไม่มี UI** เพราะเครื่องมือแก้ไขใน
   สเปรดชีตเดิมเป็นแบบ paste-from-Excel bulk importer ซึ่งจงใจไม่ทำซ้ำในระบบนี้ หน้า Work Index จึงเป็น
   read-only ทั้งหมด

8. **การย้ายพนักงานข้ามไซต์ (Employee transfers)** — `POST /api/hr/migrations` มี wrapper แล้ว แต่
   ปุ่ม "⇄" ที่กริดรายสัปดาห์เวอร์ชันเก่าเคยมีไม่ได้ถูกแสดง เพราะถ้าไม่มีข้อมูลข้อ (1) (per-employee
   absence) ผลลัพธ์ของการย้ายก็จะไม่ปรากฏบนกริดอยู่ดี ทำให้ปุ่มนี้ไม่มีประโยชน์เชิงภาพในตอนนี้

## 7. สรุปสำหรับผู้ที่ไม่ใช่สายเทคนิค

พูดง่าย ๆ ระบบนี้คือ "สมุดลงเวลาออนไลน์" สำหรับหัวหน้างานก่อสร้างที่กรอกทุกวันว่าพนักงานแต่ละคนทำงานอะไร
ที่ไซต์ไหน โดยเลือกจากรายการงานที่กำหนดไว้ล่วงหน้า (ไม่ใช่พิมพ์ข้อความอิสระ) ระบบจะคำนวณให้อัตโนมัติว่า
แต่ละไซต์มีคนทำงานกี่ "วันแรงงาน" (manday) ในแต่ละเดือน เพื่อเอาไปเทียบกับงบประมาณและต้นทุนโครงการ
มีระบบขอลาแบบออนไลน์ในตัว และมีการป้องกันไม่ให้ใครแก้ไขข้อมูลของวันที่ผ่านไปนานเกินไปแล้ว (เพื่อรักษา
ความถูกต้องของบันทึกย้อนหลัง) ยกเว้นผู้ดูแลระบบระดับสูงที่แก้ไขย้อนหลังได้ไม่จำกัด
